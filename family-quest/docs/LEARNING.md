# 학습 체크리스트 — 가족 퀘스트 앱

단계마다 "이해해야 할 것"을 적고, 본인이 설명할 수 있으면 체크한다.
각 항목은 **왜(why) → 무엇(what) → 어떻게(how)** 순서로 확인한다.

## 1단계 — 뼈대와 디자인 시스템

### A. 문제 (왜 이 단계가 먼저인가)
- [ ] 왜 데이터베이스보다 디자인 시스템을 먼저 만드는가 (이후 모든 화면이 같은 부품을 쓰므로, 부품이 늦게 바뀌면 전 화면을 고쳐야 한다)
- [ ] 왜 "토큰(면/edge/deep 3단)"으로 색을 관리하는가 (색을 바꿀 때 한 곳만 수정, 파스텔 위 글자색을 자동으로 진하게 보장)
- [ ] 왜 날짜를 기기 시간이 아니라 Asia/Seoul 기준으로 고정하는가 (서버는 UTC, 체크 기록의 "오늘"이 어긋나면 달성률이 틀어진다)

### B. 해결 (무엇을, 어떻게)
- [ ] 폴더 구조: `src/app`(경로) / `src/components/ui`(공통 부품) / `src/components/today`(오늘 화면 전용) / `src/lib`(순수 로직·데이터)
- [ ] 디자인 토큰이 어디에 정의되는가: `src/app/globals.css` 의 `@theme static` → CSS 변수 `--color-hero` 등
- [ ] `toneStyle(tone)` 이 하는 일: 톤 이름 하나로 `--face / --edge / --deep` 세 변수를 요소에 주입
- [ ] `raised-card / raised-3 / raised-4 / raised-hero` 유틸리티가 각각 어떤 입체 규칙(6절)을 구현하는가
- [ ] 7개 공통 부품의 역할과 props: Card, Button, IconTile, CheckButton, ProgressRing, ProgressBar, TabBar
- [ ] Pretendard 를 왜 `next/font/local` 로 로드하는가 (외부 요청 없이 자체 호스팅, 글꼴 깜빡임 방지)

### C. 설계 결정과 엣지 케이스
- [ ] 결정 1: 기존 저장소 루트 대신 `family-quest/` 하위 폴더에 앱을 둔 이유
- [ ] 결정 2: 오늘 날짜를 서버가 아닌 클라이언트에서만 읽는 이유 (`useSeoulToday`, Cache Components 의 "현재시각" 제한 + 하이드레이션 불일치 회피)
- [ ] 결정 3: Tailwind v4 는 클래스에서 참조되지 않는 테마 변수를 지운다 → `@theme static` 으로 모든 토큰을 강제 출력 (실제로 겪은 버그)
- [ ] 결정 4: CSS 변수 색은 `bg-(--face)` 문법을 써야 한다 (`bg-[var(--face)]` 는 v4 에서 배경색으로 인식되지 않았다)
- [ ] 엣지: lavender 구성원의 그래프 선 색이 명세(6절)에 없음 → edge 색으로 임시 대체, 확정 필요
- [ ] 엣지: 체크 토글은 1단계에서 화면 상태만 바뀐다 (저장 없음). 4단계에서 낙관적 업데이트로 교체
- [ ] 엣지: 가족 공동 퀘스트는 "참여자 전원 체크 = 성공". 비참여 구성원에게는 체크 버튼이 보이지 않는다

### D. 넓은 맥락 (이 변경이 무엇에 영향을 주는가)
- [ ] 이후 모든 화면(퀘스트, 기록, 보상, 설정)이 이 7개 부품과 토큰만으로 조립된다
- [ ] 임시 데이터(`src/lib/mock/today.ts`)의 필드명이 4절 데이터 모델과 같으므로 4단계에서 교체 비용이 낮다
- [ ] `npm run build` / `npm test` / `npm run lint` 가 단계 종료의 공통 완료 기준이다

## 보조 모듈 — 소아청소년 BMI 백분위수 (`src/lib/bmi/`)

7단계(계획 계산)의 8.3 한도 "미성년 BMI 85백분위수 미만이면 유지 계획만" 에서 쓰는 순수 함수. 화면 연결은 7단계에서 한다.

### A. 문제
- [ ] 왜 아이는 성인처럼 BMI 25 라는 고정 기준을 쓰지 않는가 (성장 중이라 성별·월령마다 정상 범위가 다르다 → 같은 성별·월령 집단 안에서의 위치 = 백분위수)
- [ ] 왜 LMS 세 값(L: 왜도, M: 중앙값, S: 변동계수)만으로 백분위수를 계산할 수 있는가 (표의 p85, p95 는 이 식의 결과를 미리 적어 둔 값)
- [ ] 왜 저체중을 BMI 로 판정하지 않는가 (지침서 기준은 "연령별 체중 5백분위수"이며 이 데이터에 없다)

### B. 해결
- [ ] 입력 → 결과 흐름: 나이(개월) → BMI(소수 1자리 반올림) → LMS 행 조회 → Z → Φ(Z)×100 → 판정
- [ ] 각 함수의 위치: `ageInMonths`, `calcBmi`, `zScore`, `percentileFromZ`, `classify`, `assessChildBmi`(종합)
- [ ] Φ(표준정규 누적분포)를 erf 근사식으로 구현한 이유와 정밀도(최대 오차 1.5e-7, 표시 단위 0.1 에 충분)
- [ ] 데이터 파일 `data/bmi_lms_2017.json` 을 코드와 분리한 이유 (2027 개정 시 교체)

### C. 설계 결정과 엣지
- [ ] 결정 1: 판정 경계는 "표시값(소수 1자리 반올림)"으로 비교 → 화면 숫자 94.96 이 "95.0" 으로 보이면서 과체중으로 판정되는 모순을 막는다
- [ ] 결정 2: 생년월만 아는 구성원(`birth_year_month`)은 일(day) 항을 빼고 월 차이만 쓴다 → 명세에 없는 규칙, 확인 필요
- [ ] 엣지: 24개월 미만(판정 안 함), 228개월 이상(범위 밖, 성인 기준 적용 여부는 기획 결정), Z ±3 초과("0.1 미만" / "99.9 초과")
- [ ] 엣지: 35→36개월 경계에서 WHO 기준 → 국내 도표로 바뀌어 값이 튀어도 오류가 아니다 (`whoRange` 플래그)
- [ ] 엣지: 표가 비어 있으면 `table_missing` → "성장도표 기준 미입력" 표시 (PLAN.md 8.3)

### D. 맥락
- [ ] 결과 유형이 `status` 로 나뉘는 이유: 화면이 "계산 불가 이유"를 그대로 안내해야 하므로 null 하나로 뭉개지 않는다
- [ ] 데이터 이용 조건(질병관리청 승인)과 비진단 문구 규칙은 공개 배포 전 확인 사항이다

## 2~9단계 — 한 번에 진행한 부분 (요약 체크리스트)

> 2단계부터는 승인 없이 진행했습니다. 결정 사항은 docs/DECISIONS.md 에 있습니다.

### 2단계 데이터베이스
- [ ] 왜 모든 테이블에 `family_id` 를 넣었는가 (RLS 정책 한 가지로 통일)
- [ ] `my_family_id()` 가 security definer 인 이유 (RLS 가 걸린 families 를 정책 안에서 읽어야 하므로)
- [ ] 잔액을 뷰로 계산하는 이유와 `security_invoker` 의 의미
- [ ] 로컬 PostgreSQL 로 RLS 를 검증한 방법 (`auth.uid()` 스텁 + `set_config('request.jwt.claims')`)

### 3단계 로그인·프로필
- [ ] 저장소 인터페이스(repo)를 둔 이유와 데모 모드가 가능한 원리
- [ ] 진입 제어(AppGate)의 세 가지 분기: 로그인 → 가족 → 구성원
- [ ] PIN 이 화면 보호일 뿐 DB 권한이 아닌 이유 (가족 계정 1개 구조)

### 4·5단계 체크·달성률
- [ ] 낙관적 업데이트의 흐름: 화면 먼저 → 저장 → 실패 시 되돌림 → 성공 시 재조회
- [ ] 실시간 반영 원리 (Supabase: postgres_changes 구독 / 데모: storage 이벤트)
- [ ] 주 N회 목표의 "예정" 계산식과 그 이유
- [ ] 가족 공동 목표의 하루 성공 조건

### 6단계 보상
- [ ] 신청 → 승인(차감) → 지급의 세 상태와 잔액이 바뀌는 시점
- [ ] 개인 스티커와 가족 스티커가 섞이지 않는 구조

### 7단계 계획
- [ ] 성인 공식에서 D(기본 조정량)가 적응 단계를 2/3 로 두고도 총 감량이 맞는 이유
- [ ] 8.3 한도 4가지가 각각 어디서 검사되는가
- [ ] 단계 통과 판정이 "앱이 열릴 때" 실행되는 구조와 중복 방지 키
- [ ] 미성년 계획이 성인과 다른 세 가지 (속도, 비율, 식단 방식)

### 8·9단계
- [ ] 제안/승인 흐름에서 `created_at` 을 승인 시각으로 바꾸는 이유
- [ ] PWA 설치에 필요한 세 가지(매니페스트, HTTPS, 아이콘)와 서비스 워커가 캐시를 하지 않는 이유

### 상단 바·이용방법 (추가 요청)
- [ ] 상단 바를 각 화면이 아니라 `AppShell` 한 곳에 넣은 이유 (화면마다 중복하지 않고, 빼거나 바꿀 때 한 곳만 고침)
- [ ] 뒤로가기가 "기록이 없으면 홈으로" 처리하는 이유 (주소로 바로 들어온 경우)
- [ ] `/guide` 가 로그인 전에도 열려야 하는 이유와 `AppGate` 가 그것을 허용하는 방식
- [ ] 앱에 원본 PNG 대신 축소 WebP 를 넣은 이유 (1.5MB → 364KB)
